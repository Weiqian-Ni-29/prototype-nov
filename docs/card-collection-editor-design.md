# 《维洛丹》卡牌收藏与卡组编辑界面设计

> 实施设计稿 v1.0 · 2026-11-20
> 基线：`main@91bf91a`
> 范围：当前主战者战棋体系中的卡牌收藏与远征卡组编辑，不修改战斗规则。
> 本文描述待实施改动，不代表这些界面能力已经实现。

## 1. 背景

当前版本已经具备可用的卡组编辑器：玩家可以浏览持有卡牌，按类型与元素筛选，搜索卡名、效果和攻击类型，查看选中卡详情，加入或移除卡牌，并在装备详情中进行强化。遭遇战前还会显示主战者、战前准备和敌方主战者信息。

现有界面的主要问题不是功能缺失，而是浏览与组牌反馈不够集中：

- 收藏卡面较小，费用没有直接出现在收藏网格中，玩家需要逐张选中才能比较。
- 类型、元素与文本搜索已经存在，但缺少直观的费用筛选。
- 右侧牌表表达当前数量，却没有按费用组织，也无法快速判断牌组费用分布。
- 加入、移除、同名上限与出战条件分散在不同区域，状态变化可以进一步统一。
- 当前界面需要保留自己的规则与美术身份，不能照搬炉石的职业、合成和固定 30 张牌组体系。

## 2. 设计目标

1. **一眼比较**：费用、卡名、类型、元素、已入牌组数量和同名上限在收藏卡面上同屏可见。
2. **快速定位**：类型、元素、费用和文本搜索可以叠加，当前筛选状态清晰且能一键清空。
3. **低误操作**：浏览卡牌与修改牌组是明确分离的动作；加入、移除后立即给出同步反馈。
4. **读懂牌组**：右侧按费用聚合排序，并提供简洁费用分布，帮助玩家检查构筑。
5. **保持规则一致**：最低 3 张出战、无总张数上限、同名限制、草稿保存、装备强化和战前准备均沿用当前逻辑。
6. **可实施、可回归**：优先扩展现有编辑器与 UI 组件，不引入新的牌组系统或战斗规则。

## 3. 非目标

本期不做以下功能：

- 不引入职业、阵营或卡牌稀有度筛选。
- 不引入 30 张牌组、固定牌组上限或自动补满牌组。
- 不引入卡牌合成、分解、奥术之尘或卡包管理。
- 不引入多牌组栏位、牌组命名、牌组代码、导入导出或牌组推荐。
- 不修改抽牌、法力、部署、走棋、反击、疲劳、主战者胜负等战斗规则。
- 不接入骰子、无主战者或战斗天气等仍处于其他讨论稿中的方向。
- 不做牌表手动排序；牌表按费用自动组织。
- 首版不承诺手机触屏布局，只保证当前桌面窗口与窄桌面窗口可用。

## 4. 设计依据

### 4.1 外部交互参考

炉石收藏与组牌界面中值得借鉴的是信息组织方式，而不是其游戏规则或素材：

- 收藏与组牌共用同一页面，左侧浏览大卡面，右侧显示当前牌表。
- 文本搜索可以与费用等视觉筛选组合，减少在不同页面之间反复跳转。
- 收藏卡直接表达持有或入组状态，玩家不必依靠记忆判断还能加入几张。
- 牌表提供连续的数量反馈，费用曲线作为构筑摘要，而不是独立的复杂分析页。

参考资料：

1. Blizzard，[Managing the Collection Manager](https://hearthstone.blizzard.com/en-us/news/21790299)。
2. Hearthstone Wiki，[Collection manager](https://hearthstone.wiki.gg/wiki/Collection_manager)。

### 4.2 当前实现基础

主要涉及文件：

- `game/scripts/presentation/card_deck_editor.gd`
  - `setup()` 构建页面、筛选、详情、收藏网格与右侧牌表。
  - `_filter()` 负责类型、元素和文本筛选。
  - `_add_tile()` 绘制收藏卡。
  - `_render_selection()` 绘制详情、强化和加入按钮。
  - `_render_deck()` 绘制数量、移除和出战提示。
- `game/scripts/presentation/card_ui.gd`
  - 提供现有色板、卡面美术、属性图标、攻击类型标签和通用控件。
- `game/scripts/domain/card_catalog.gd`
  - 提供卡牌定义、持有集合、同名限制、费用和牌组合法性。
- `game/scripts/domain/expedition.gd`
  - 保存牌组、强化装备并管理战前准备。
- `game/tests/test_battle_ui.gd`、`game/tests/test_chess_loadout.gd`
  - 作为后续 UI 与规则回归的主要测试位置。

本期应优先修改表现层和对应测试，不改变领域规则的含义。

## 5. 页面结构

### 5.1 总体布局

区域职责：

| 区域 | 主要职责 | 不应承担 |
| --- | --- | --- |
| 顶部标题 | 标识页面与抽牌提示 | 堆叠战斗规则说明 |
| 筛选区 | 缩小收藏结果 | 修改牌组 |
| 选中详情 | 阅读完整效果、强化、加入 | 长期占用大量纵向空间 |
| 收藏网格 | 比较卡牌与入组状态 | 显示整段效果文案 |
| 右侧牌表 | 查看当前牌组、移除卡牌 | 手动排序或编辑多张牌组 |
| 费用分布 | 汇总当前牌组费用 | 评价牌组强弱或自动补牌 |
| 底部操作 | 保存、返回或开始战斗 | 隐藏牌组合法性反馈 |

### 5.2 尺寸与响应式

以当前逻辑视口 1440×900 为主要设计尺寸，同时验证 1280×800 窗口：

- 页面外边距建议 20，左右栏间距 16。
- 宽屏右侧栏建议宽 300；窄桌面可降为 240。
- 可用宽度不低于 1100 时，收藏网格使用 4 列；低于 1100 时使用 3 列。
- 收藏卡建议最小逻辑尺寸约 160×224，卡面美术保持现有居中裁剪，不拉伸人物。
- 收藏区与右侧牌表分别纵向滚动；页面自身不得出现横向滚动条。
- 选中详情在窄屏允许效果文本换行，加入按钮保持可见，不得被挤出页面。
- 右侧牌表、费用分布与底部操作之间优先压缩留白，不压缩文字到难以阅读。

## 6. 收藏卡设计

每张收藏卡包含以下信息：

1. **费用**：左上角小型蓝绿色费用徽记，使用整数费用。
2. **卡面美术**：沿用现有伙伴肖像、装备图标和法术图标，不引入炉石卡框。
3. **卡名**：单行优先，过长时省略号；完整名称进入无障碍名称与详情。
4. **类型与元素**：使用短文本和现有六元素图标，例如“法术 · 火”。
5. **入组数量／上限**：例如 `0/1`、`1/2`、`2/2`，直接读取当前编辑中的牌组。
6. **选中状态**：旧金描边，并同步更新上方详情；不能只依赖颜色表达选中，详情标题也必须一致。

数量状态：

- 未达到上限：使用正常对比度，详情按钮显示“＋ 加入牌组”。
- 达到上限：数量保持可读，详情按钮显示“已达同名上限”并禁用。
- 未加入：显示 `0/上限`，不使用红色或缺失卡牌的灰化效果，因为该卡已经持有。
- 数量变化后不得重置搜索、筛选、选中卡或收藏滚动位置。

收藏卡不显示完整效果正文，避免重新变成密集的小字列表；完整效果放在选中详情中。

## 7. 筛选与搜索

### 7.1 筛选维度

首版提供四组可叠加条件：

| 条件 | 选项 | 规则 |
| --- | --- | --- |
| 类型 | 全部、伙伴、装备、防御、法术 | 沿用当前可见类型，不新增职业 |
| 元素 | 全部、地、火、水、冰、风、雷 | 使用现有图标与提示 |
| 费用 | 全部、1、2、3、4、5+ | `5+` 表示费用大于等于 5 |
| 文本 | 卡名、效果、攻击类型 | 沿用当前搜索范围与不区分大小写行为 |

不同维度之间取交集，同一维度单选。默认状态为“全部类型、全部元素、全部费用、空搜索”。

示例：

- 选择“法术 + 火 + 1费”，只显示同时满足三项的卡牌。
- 再输入“伤害”，结果还必须匹配文本条件。
- 牌组中已有几张牌不影响收藏筛选结果。

### 7.2 清空与空结果

- “清空筛选”恢复四项默认条件，不清空当前牌组。
- 没有结果时，收藏网格显示“没有符合条件的卡牌”，并保留“清空筛选”入口。
- 空结果不得清空右侧牌表，也不得弹出阻断式对话框。
- 若当前选中卡仍在新结果中，保持选中；否则选中第一张结果。没有结果时，详情区域显示空状态。
- 高级查询语法，例如 `mana:1`、`attack:2+`，不在本期验收范围内；首版用明确的视觉控件完成费用筛选。

## 8. 加入、移除与拖拽

### 8.1 浏览与修改分离

- **单击收藏卡**：只选中并查看详情，不修改牌组。
- **点击详情中的“＋ 加入牌组”**：加入一张当前选中卡。
- **拖拽收藏卡到右侧牌表**：加入一张该卡。
- **点击右侧牌表某一行的减号或整行按钮**：移除一张该卡。

这样保留当前“选中详情后添加”的可理解性，同时获得参考界面的快速拖拽能力。首版不做双击加入，避免与单击选中形成不确定行为。

### 8.2 合法性与反馈

- 加入前使用 `Cards.limit(id)` 判断同名上限，不能以按钮是否可见代替规则校验。
- 达到上限后，拖拽和按钮均不得继续加入，也不得覆盖其他卡。
- 移除只移除一张；数量为 1 时移除该行，数量大于 1 时只减少计数。
- 每次成功加入或移除后，在同一轮刷新中同步：
  - 收藏卡 `已入/上限`；
  - 详情按钮与上限文案；
  - 右侧牌表行与总数；
  - 费用分布；
  - 出战条件提示。
- 失败的拖放不改变任何状态，并通过现有行内错误区域说明原因，例如“这张牌已达同名上限”。
- 拖拽只以卡牌 ID 为数据，不复制卡牌实例，不修改持有装备或伙伴。

### 8.3 焦点与滚动

- 加入后保持当前选中卡，焦点留在加入按钮；达到上限时焦点移至对应收藏卡。
- 移除后优先聚焦同一牌表行；该行消失时聚焦相邻行或右侧牌表标题。
- 重新绘制网格与牌表时保留有效滚动位置，不得每次回到顶部。
- 拖拽不是唯一操作路径，所有能力都能通过鼠标点击和键盘完成。

## 9. 右侧牌表

### 9.1 聚合与排序

- 每种卡牌只显示一行，格式为“费用、卡名、×数量、移除按钮”。
- 默认按费用升序；同费用内保持当前收藏目录的稳定顺序，避免每次操作跳动。
- 牌表显示编辑中的临时牌组，不直接修改存档，直到现有保存或开始战斗流程确认。
- 牌表顶部显示“远征卡组”和“当前张数”，例如 `11张 · 至少3张`。
- 无总张数上限，不出现 `11/30`、进度环或“还需补满”的文案。
- 空牌组显示“从左侧加入卡牌”，并保留保存草稿和开始战斗各自不同的合法性行为。

### 9.2 保留的战前信息

以下现有内容继续位于右侧栏上部：

- “旅人 · 主战者”，表示主战者开局站场，不计入牌组张数。
- 生命之种等已经生效且需要展示的常驻状态。
- 遭遇战中的战前准备选择与效果说明。
- 已知敌方主战者信息。

这些信息不计入费用分布，也不作为可移除牌表行。

## 10. 费用分布

- 仅统计当前编辑牌组中的卡牌，不包含主战者、战前准备、持续遗器或收藏中未加入的卡。
- 分桶与费用筛选一致：1、2、3、4、5+。
- 每个分桶显示数量与横向条形，条形长度相对本牌组最大分桶归一化。
- 数量为 0 的分桶可以保留但显示空条，避免加入高费卡时布局突然跳动。
- 每次加入、移除、替换编辑牌组或载入已有牌组时重新计算。
- 费用分布只是描述性信息，不显示“曲线差”“推荐补牌”或自动完成按钮。

默认 11 张示例牌组可用于视觉回归：1 费 8 张、2 费 3 张。该示例不是对玩家牌组的固定要求。

## 11. 选中详情与装备强化

选中详情包含：

- 卡面美术、卡名、费用、类型、元素与攻击类型。
- 完整效果文本，允许换行。
- 伙伴的攻击、生命、护甲等现有摘要。
- 加入按钮或同名上限状态。
- 对实际装备实例，继续显示当前强化等级、下一等级、灯铢价格与强化按钮。

装备强化沿用 `run_model.enhancement_quote()` 和 `run_model.enhance_card()`：

- 牌组继续引用同一个装备实例 ID，强化不得复制卡牌或改变数量。
- 强化成功后刷新收藏、详情、牌表与费用分布，以实际返回的新定义为准。
- 灯铢不足时按钮禁用；失败原因沿用现有 `show_error()`。
- 强化流程不得重置战前准备或未保存的牌组编辑。

## 12. 保存、出战与合法性

当前规则保持不变：

- 开局抽 3 张，最低 3 张才能出战。
- 牌组没有总张数上限。
- 伙伴和实际装备等唯一卡遵循每种 1 张；防御、法术等行动卡遵循每种 2 张，具体以 `Cards.limit()` 为准。
- 非遭遇编辑允许保存不足 3 张的草稿；这与“可以出战”是两个不同条件。
- 遭遇战中不足 3 张时，“开始战斗”禁用，并显示“再加入 X 张即可出战”。
- 非遭遇编辑的“保存卡组”仍由 `Expedition.save_card_deck()` 做最终合法性校验，失败时显示返回信息。
- 开始战斗前仍须由领域层验证持有状态与同名上限，UI 校验不能成为唯一防线。

状态文案：

| 状态 | 提示 | 主要按钮 |
| --- | --- | --- |
| 0–2 张，遭遇战 | 再加入 X 张即可出战 | 开始战斗禁用 |
| 0–2 张，普通编辑 | 当前为草稿，再加入 X 张即可出战 | 保存卡组按现有规则处理 |
| 3 张及以上 | 已满足出战条件 | 开始战斗可用 |
| 同名达到上限 | 已达同名上限 | 加入按钮禁用 |
| 保存失败 | 显示领域层返回原因 | 保留当前编辑内容 |

## 13. 视觉与可访问性

沿用 `card_ui.gd` 的现有视觉语言：

- 主金色 `GOLD #dec38e`。
- 正文 `INK #ede6cf`。
- 次要文字 `MUTED #b1c3b5`。
- 成功或友方辅助 `GREEN #aad5b6`。
- 警告 `ORANGE #efb58f`。
- 面板背景 `#213b33`，边框 `#657e6c`，主按钮背景 `#dac18c`。

要求：

- 费用徽记采用与现有界面协调的蓝绿色，不直接复制炉石的蓝色水晶造型。
- 卡牌选中、达到上限、禁用和错误状态都必须同时具有文字或形状反馈，不能只靠颜色。
- 元素图标保留 tooltip 与无障碍名称。
- 收藏卡按钮的无障碍名称至少包含卡名、费用、当前入组数与上限。
- 正文与关键数量在当前桌面缩放下清晰可读，效果文本不以过小字体强行塞入卡面。
- 动画只使用轻微 hover、选中和拖放高亮，不加入遮挡牌表的粒子或长动画。

## 14. 状态与异常覆盖

后续实现必须检查以下状态：

1. 默认 11 张牌组首次打开。
2. 空牌组与不足 3 张的草稿。
3. 搜索无结果，以及清空筛选后恢复。
4. 筛选后选中卡被排除。
5. 同名卡从 0 加到上限，再尝试按钮与拖拽加入。
6. 多张同名卡逐张移除，直至该行消失。
7. 长卡名、长效果和多行强化信息。
8. 只有低费卡、只有高费卡及空牌组的费用分布。
9. 装备强化成功、灯铢不足和强化失败。
10. 战前准备切换后继续编辑牌组。
11. 遭遇战与普通编辑两种入口。
12. 收藏和牌表长列表滚动后加入、移除与刷新。

## 15. 实施建议

### 15.1 表现层

在 `card_deck_editor.gd` 内扩展：

- 增加费用筛选状态与筛选条件。
- 在 `_add_tile()` 中补费用、元素和更清晰的入组数量。
- 将加入、移除后的公共刷新集中管理，避免多个操作只更新部分区域。
- 在 `_render_deck()` 中按费用稳定排序，并绘制费用分布。
- 为收藏卡到右侧牌表增加拖放，但保留现有按钮路径。
- 保存和恢复有效的选中、焦点与滚动状态。

在 `card_ui.gd` 中只提取确实被多个位置复用的视觉组件，例如费用徽记或费用条；不要为单次使用建立大型新组件体系。

### 15.2 领域层

- 优先复用 `Cards.owned_definition()`、`Cards.limit()`、`Cards.valid_deck()` 与现有保存接口。
- 费用分布是表现层对当前牌组的聚合，不新增第二份牌组数据。
- 若需要测试排序或分桶，可放置小型纯函数，但不得改变 `Cards.limit()` 或最低出战张数的语义。

### 15.3 测试

后续代码实现时至少补充：

- 类型、元素、费用、文本的交集筛选与清空。
- 加入、移除、同名上限和拖拽拒绝。
- 牌表费用排序、聚合数量与费用分布。
- 操作前后选中、滚动和战前准备保持。
- 不足 3 张的草稿保存与遭遇战禁用行为。
- 默认 11 张和无总张数上限的回归。
- 装备强化后的详情、数量与费用刷新。
- 1440×900 与 1280×800 下无重叠、无横向页面滚动。

文档 PR 本身不运行游戏测试；实现 PR 必须运行对应 Godot 测试。

## 16. 验收标准

### 收藏与筛选

- [ ] 收藏卡同屏显示费用、卡名、类型或元素、已入数量与上限。
- [ ] 类型、元素、费用和文本搜索可叠加，清空筛选不影响牌组。
- [ ] 无结果、选中变化与长文本均有可用表现。

### 组牌交互

- [ ] 单击只选中；详情按钮和拖拽均可加入，右侧可逐张移除。
- [ ] 同名上限在按钮与拖拽两条路径上都生效。
- [ ] 加入或移除后，收藏、详情、牌表、总数、费用分布和出战提示同步。
- [ ] 操作不会意外清空筛选、重置滚动或丢失战前准备。

### 牌表与规则

- [ ] 牌表按费用稳定排序，每种卡一行，数量准确。
- [ ] 费用分布只统计当前牌组，不包含主战者或遗器。
- [ ] 不出现 30 张上限、自动补牌、职业或合成系统。
- [ ] 不足 3 张的草稿保存和遭遇战禁用行为与当前规则一致。
- [ ] 装备强化、主战者与战前准备入口保持可用。

### 视觉与可访问性

- [ ] 使用现有墨绿、旧金、六元素和手绘卡面风格。
- [ ] 所有拖放能力均有点击与键盘替代路径。
- [ ] 状态不只靠颜色表达，焦点与无障碍名称完整。
- [ ] 1440×900 和 1280×800 下主要操作可见、文字不重叠、页面无横向滚动。

## 17. 完成定义

本设计实施完成需要同时满足：

1. 上述验收项通过，且现有战斗、商店、招募、装备强化和遗器回归没有因编辑器改动失败。
2. 玩家能从打开编辑器开始，完成筛选、查看详情、加入、移除、检查费用分布并保存或出战，不需要进入第二个页面。
3. 界面中的所有数量与合法性都能追溯到当前编辑牌组和现有领域规则，没有另建一份容易失同步的状态。
4. 设计、示意图、实现与测试对“最低 3 张、无总张数上限、同名限制”的表述一致。
